## Findings in the initial reviewed revision

The numbered findings below refer to the initial hashes above. The follow-up section records the parent's corrections that were subsequently reread; do not report already corrected items as still present in the revised hashes.

1. **Missing baseline can still become candidate PASS.** `matrix.py:142-157` labels a successful process PASS, and compares only if `before/<case>/run-01.stable.json.gz` exists. A non-before phase with no matching baseline silently skips equality and retains PASS. Initial before/run01 may legitimately have no reference; every candidate comparison must instead require the reference plus successful matching baseline metadata. This blocks using script PASS alone as the zero-difference gate.

2. **Resume reuses metrics without verifying the current evidence identity.** `matrix.py:111-113` returns any existing metrics file before reading the current RAW, assembling the current command or checking Source. A changed case, RAW or source-root at the same phase/case/repeat path therefore returns a stale PASS and stale measurements. Require matching normalized workload/command and immutable Source/input manifests plus retained-output hashes, or fail closed and use a new evidence namespace. Preserve the existing artifacts rather than overwriting them. The parent can separately prove that existing baseline runs were fresh and no inputs/Source changed; this finding does not itself prove a current baseline run is stale.

3. **Recorded failures do not propagate to process exit status.** `matrix.py:181-188` breaks a failed case's repeat loop but neither aggregates failure nor exits nonzero; it proceeds to the next case and `main()` returns normally. `instrumented.py:170-177` likewise saves/prints FAIL but returns a successful Python process exit. A shell command can therefore report exit 0 even when equality or warm stability fails. Return a nonzero status for FAIL/INCOMPLETE or enforce a separate metadata validator before accepting any command result. The first-difference payload remains useful and is not discarded.

4. **GraphSnapshot does not preserve mutable-set alias topology.** In `instrumented.py:37-39`, set/frozenset handling occurs before identity registration, and each member is encoded with a fresh GraphSnapshot. One shared mutable set referenced by two fields and two distinct equal sets consequently have the same encoding. This contradicts the class's object-aliasing claim and can miss a changed shared-mutation contract. Register container identity first; order set members with a separate deterministic canonical key, then encode their actual values using the shared graph. Preserve object alias edges across set members and the rest of that snapshot. No runtime probe was needed to identify this direct control-flow gap.

5. **Warm wall/CPU intervals include evidence I/O and comparison work.** `instrumented.py:124-134` starts before state calculation but samples elapsed wall/CPU only after JSON encoding, raw output write, stable parsing/encoding and baseline gzip read/decompression. The reported warm measurements are end-to-end instrumented probe cost, not isolated repeated Engine calculation. Store calculation-end timestamps immediately after the intended calculation/serialization boundary, and keep evidence writes/comparison outside that measurement; alternatively retain the current numbers explicitly labeled as including verification overhead. Warm probes must remain separate from normal cold-CLI performance conclusions.

6. **Native capture is not itself native equality verification.** `instrumented.py:162-171` saves native graphs/index but sets its equality status solely from serialized stdout versus the baseline CLI. There is no native before/after comparator in these two scripts. This is valid collection tooling, but its PASS cannot establish native object equality. A separate gate must compare complete ordered hook indexes/stage labels and every decompressed graph with no unexplained field, type, alias, ordering or value difference; retain first native divergence. Compare the same workload/configuration and fail on missing or extra hooks/files.

## Coverage boundaries to report accurately

- Native dataclass encoding includes every declared dataclass field and any dynamic `__dict__` additions (instrumented 50-53). Dict/list/tuple traversal preserves ordering and intra-snapshot aliases through tokens/refs (40-49). Decimal text, datetime ISO/fold and exact timedelta parts are represented explicitly. The `keepalive` collection prevents temporary field dictionaries from being garbage-collected and reusing IDs during encoding; it is necessary for the current token scheme.
- Slot-only non-dataclass objects fall through to type-only output (57). Current `MarketChronology` is such an object. This encoder therefore cannot be described as universal native field coverage. Either add slot traversal for contract-relevant captured objects or document the explicit exclusions.
- Native stage roots are selective projections, not complete MarketContext/FullDirectionState/PipelineState state. The market projection omits `index_offset`, initial-regime flags, chronology and lower index (93-94). Full-direction projection includes emitted collections, accepted E/S audit and eligible A, but omits other detector ownership/query state (95-98). Pipeline projection omits `directions`, `reusable_full_context`, detector objects, both invalid-identity maps, full S candidates and `primary_result` (99-101). Later range and final-visibility dataclasses are captured directly; primary result is captured by its own hook. Document those boundaries instead of claiming every internal detector field/cache has been compared.
- A fresh GraphSnapshot is created for each hook (83). Aliases are comparable within a captured graph, not across hook invocations. This is reasonable for independent stage snapshots, but does not establish that a particular Python object persisted between stages; physical identity/domain provenance must still be compared by native fields and cross-stage joins.
- Profile/allocation/snapshot instrumented durations are correctly separated by mode and labeled instrumented. Snapshot JSON building and `keepalive` materially add memory/CPU. Allocation mode starts tracing after Bridge module import and before `bridge.main`; it measures Python-traced allocations for that interval, not OS process startup/full peak working set. No instrumented duration should replace normal CLI timing.
- Warm mode deliberately reuses the loaded EngineBundle and MarketContext across six calculations, including chronology/module caches; first iteration is flagged warmup. It tests this repeated-input in-process scenario, not a fresh CLI or a multi-input cache-lifetime scenario. Every repeated raw payload is saved and compared to the before CLI output, which is a useful stale-state guard on the exercised input.

## Checks that look correct by inspection

- `matrix.command` uses the supported Bridge aliases and includes direction, timeframe, presentation bounds, optional lifecycle, primary and Bridge-output configuration. The complete workload manifest includes synthetic and multiple complete RAW scopes, both directions, more than one timeframe, primary-disabled, lifecycle-disabled and narrow-presentation cases. Coverage quantity is not evidence of completed execution.
- Cold runs use an independent fresh Python process and sequential polling. `-B` plus `PYTHONDONTWRITEBYTECODE` avoids ordinary bytecode writes. stdout is redirected directly to a retained binary file, stderr is retained, and raw stdout byte count/hash is recorded. Failures/timeouts retain outputs. File hashing occurs outside the measured child interval, except the separately reported after-run validation.
- Stable comparison removes only root `timings`, the explicit Bridge telemetry envelope (Bridge 3386-3391). All other root values, dict insertion order, array ordering, key/value types, public versions and Decimal strings remain in comparison. `first_diff` checks exact Python types and dict key order before recursive values. No version/schema/identity/Decimal field is normalized away. Canonical JSON bytes are not verbatim wire bytes; raw original stdout remains available for forensic or lexical checks. Adding further exclusions would require separate authorization and explanation.
- The Windows memory structure matches PROCESS_MEMORY_COUNTERS layout: two DWORDs followed by eight SIZE_T fields, with PeakWorkingSetSize at `peak`. HANDLE uses the actual Popen handle; API argtypes use pointer-sized HANDLE and FILETIME pointers. `GetProcessTimes` sums kernel+user FILETIME in 100ns units and divides by 10,000,000. A final update is attempted after `wait`, while Popen still owns the handle, which permits complete CPU-time retrieval when the API succeeds. No unit or precision error was found in this layout/conversion by inspection.
- Memory polling reads the OS cumulative PeakWorkingSetSize, not merely current working set, so a short spike occurring before a successful later sample remains represented. As already disclosed by the parent, memory queries may cease to succeed after exit and the last polling tail can remain unobserved. Report sampled OS peak with that qualification, not an exact guaranteed lifetime peak. API success counts/errors are not recorded; require usable non-null CPU and nonzero memory evidence before treating those metrics as measured rather than silently accepting their initial values.
- All currently listed production output prices are strings and public times/indices are integers; the stable parser retains their exact text/type. Original RAW is never rewritten by these scripts. Resume validation and Source/harness identity still need the gates above for reproducible evidence.
