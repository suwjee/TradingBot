## Ownership and data flow

`order_audit_engine.py` owns physical Order discovery, source/stop geometry delegation, creation-cause registration, reuse queries, historical retention, and final accepted identity/cause preparation. E supplies the `OrderAuditEngineMixin` runtime context; S supplies `SOrderAuditMixin`. `MarketChronology.canonical_order_stop` remains the source of canonical stop geometry. The bridge/lifecycle module imports the Order owner rather than implementing an alternative ledger.

The Order_B path builds exact Reset events, same/opposite Reaction chronology, accepted dominant post-stop owners, and source-tied behavior anchors. Each eligible Reset chooses the latest already-confirmed same-direction Reaction for that First, latest strictly earlier accepted stop, and latest strictly earlier behavior source. It freezes the inclusive directional anchor-to-First extreme, requires strict extension and an extreme source before First, then finds the first strict lower-RAW break after Reset. The calculation candle containing the break gates the canonical opposite Reaction; exact confirmation must follow the break. An accepted A in or before that break candle expires the leg. Registration merges all proven reset-leg causes onto the physical identity without replacing independent parent-stop causes.

The E-facing path selects direct parent-stop candidates and reset-leg candidates, resolves one physical parent-stop owner, observes decision deadlines, and exposes carried/gate-owned/post-stop accepted routes to E. Audit rebuilds preserve valid historical creator provenance, remove disowned S creator rights, and restore the secondary confirmation index with restored identities. `prepare_order_audit` merges accepted S and E ledgers, preserves first encountered physical entry, deduplicates causes, retains required out-of-window identities, and resolves the unique parent-stop cause owner before serialization.

`PL_PH_detector.py` owns independent primary-cycle state and final physical primary naming. It consumes finalized native audit projections; it does not create physical Reactions. `_matching_seeds` uses the shared dominant-owner transition. Each actual qualified reference break freezes an independent MBL candidate. `_next_point` clones local checkpoint list state and proposes a future decision without committing native ownership. `detect_bearish` interleaves activations and proposals globally. Only the earliest committed main-primary point invokes the native callback, then all pending proposals are invalidated. The callback registers native PH/PL parent-stop ownership and re-prepares the accepted audit in bridge lines 3162-3170. That mutation boundary is central to correctness.

The bullish path reflects only primary-state coordinates and price-index predicates, then restores original price/kind/direction. Native audit selection and callbacks continue in original coordinates. `_ReflectedChronology` shares original time arrays and lower index through an adapter, but allocates one wrapper per main and lower row. `_negate_price` uses `Decimal.copy_negate`, preserving long lexemes under a reduced Decimal context.

## Static complexity and candidate ranking

Let N be main rows, L lower rows, R trend Reactions, O opposite Reactions, Q Resets, B accepted behavior lifetimes, A live audit identities, C primary cycles, P committed points, and K distinct query contexts. Range-index query costs depend on the unchanged Reaction index implementation. No asymptotic estimate below substitutes for profiles.

1. **First canonical match instead of full S suffix materialization — strongest bounded candidate after profiling.** Order 2109-2128 bisects confirmation but scans/materializes every later eligible Reaction, caches the entire tuple, and copies it to a list. Its only production caller found by live search (2065-2066) takes `[0]`. Static worst retained query references can approach O(K*O). A dedicated first-match path could stop at the first qualifying row and retain only one tuple per stop, preserving the existing full-list helper if compatibility requires it. Keep exact `(confirmation, first, break, ordinal)` order, `confirmation > stop`, main-candle First gate, canonical object/number, and cached `None`. S first audits all A (1232-1233), then repeats `_first_order_after` for eligible A (1252-1256). Reusing whole results across those calls is more risky because the separate `initial_order_geometry` callable and returned object lifetime must be proven; optimize canonical suffix selection first. Required checks include independent noncanonical Order_A, nested geometry, strict stop/confirmation, mode B and both directions.
2. **Avoid temporary suffix/range slices — small allocation candidate.** Initial carried/post-stop queries materialize `records[left:right]`, `confirmation_records[start:]`, and confirmation-index suffixes (1455,1508,1515-1517); S lower fallback slices lower rows (2216), and canonical S match scans a tuple-list suffix (2124). Index iteration can preserve the same first/last order while avoiding temporary container copies. Prove source sequences are not mutated during iteration, preserve actual object references and exception behavior, and measure allocations/runtime before accepting. No trading predicate changes are needed.
3. **Reset-leg closed-range extreme query — conditional indexing candidate.** Each Reset scans anchor source through Reaction First (266-269), potentially O(Q*N), in addition to current-Reaction filtering and an O(O) physical lookup (322-326). A run-local high/low range index with earliest-equal source could reduce repeated extreme work. Preserve inclusive endpoints, anchor extension, source-before-First, Decimal values and exact selected source. Index build/retained size can outweigh benefits for few resets. Opposite lookup has two predicates, one on First index and one on confirmation; a simple bisect on one field is not equivalent and must not replace the first qualifying tuple without proof.
4. **Primary native immutable metadata view per accepted-ledger revision — conditional, wider candidate.** Every `NativePrimaryOrders.__call__` scans owner audit, resolves confirmations/creation kinds, builds records, selects first direct, and allocates/deepcopies each eligible StructureOrder (531-568). Many pending proposals are correctly replayed after commits. Hoist only immutable per-ledger metadata if profiles show repeated cost, with explicit invalidation at native audit mutation/re-preparation. List identity/length is not enough: causes/labels can mutate without membership change, and tests mutate prepared records in place. Keep snapshot deep copies or prove equivalent isolation. Never cache a negative primary proposal across commit.
5. **Dominant stop and mutable carried-audit queries — conditional indexing candidate.** `dominant_post_behavior_stops` constructs the active set for each stopped behavior (71-114), O(B^2), with object-identity ownership, inclusive end events, and deterministic rank. An event sweep is possible only with careful joint-event rank handling. `_carried_orders_for_parent` scans all live audit and creation causes for each uncached context (1422-1449), then range-filters initial records and sorts. A creation-event index must represent earliest parent cause and every reset cause and survive all cause-only mutations. Both are more invasive than the first two candidates.
6. **Primary recomputation/reflection allocations — profile before design.** Every committed main point re-runs final physical reconciliation and strict primary3 crossing discovery (365,101-172), and each main commit clears pending proposals. With many cycles this can multiply scans/copies of growing point lists; pending proposals clone highs/lows/order lists (417-419). This invalidation is semantically required. `_ReflectedChronology` additionally allocates O(N+L) wrapper objects (604-605); a lazy indexed view may reduce peak memory while preserving exact source and price access, but sequence/API behavior and traversal cost need testing. Do not introduce persistent caches, arbitrary cycle caps, clipped history, or concurrency to mask this work.

Other repeated work includes linear deep-equality cause deduplication and per-append cause sorting (19-31,1002-1008,1915-1919), full audit traversal for primary reparenting/relabeling, and repeated parent lookup scans during rebuild (1682-1688,1701-1705). These remain secondary candidates until measured; replacing dict/list equality with approximate/hash identities risks nested provenance and stable ordering.
